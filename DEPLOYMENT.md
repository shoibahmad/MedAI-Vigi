# Deploying PhenoRx to Render

The repository ships a Render blueprint (`render.yaml`) and a multi-stage
`Dockerfile`. One web service runs both halves of the app: Flask serves the JSON
API and the built React SPA from the same origin.

## Quick start

1. Push this repository to GitHub (already done for `shoibahmad/MedAI-Vigi`).
2. In Render, choose **New → Blueprint** and point it at the repository.
   Render reads `render.yaml` and creates the `phenorx` web service.
3. Set the one secret it needs, under **Environment**:

   | Key | Value |
   |---|---|
   | `NVIDIA_API_KEY` | your key from <https://build.nvidia.com/> |

   Everything else is declared in the blueprint. `SECRET_KEY` is generated by
   Render on first deploy and kept across subsequent ones.
4. Deploy. The first build takes roughly 6-10 minutes, mostly installing
   scikit-learn and building the frontend.

The service is healthy when `/health` returns 200 with `ml_model.loaded = true`.

## One service, one origin

There is a single Render service. The Dockerfile builds the SPA in a Node stage
and copies `client/dist` into the Python stage, and `routes/views.py` serves it:

| Request | Served by |
|---|---|
| `GET /`, `/assessment`, `/report`, ... | the SPA shell, from `client/dist` |
| `GET /assets/*` | the hashed Vite bundles |
| `GET /health`, `POST /predict`, `/api/*` | the Flask API |

The frontend configures no API host. `client/src/lib/api.js` sets
`baseURL: '/'`, so every call is same-origin and nothing needs rebuilding when
the service URL changes. There are no `VITE_*` values baked into the bundle.

Because it is same-origin, CORS is off by default. Development still gets it,
for the Vite server on :5173, and `CORS_ORIGINS` accepts an explicit
comma-separated list if you ever do split the frontend out.

## Why Docker rather than the native Python runtime

The frontend is a Vite build, and Render's Python image does not provide Node, so
`npm ci` would fail during the build. The Dockerfile builds the SPA in a Node
stage and copies `client/dist` into the Python stage, which also keeps Node out
of the final image.

## Why the model is not trained during the build

`scripts/model_trainer.py` works, but building the model on Render is a poor
trade:

- it needs `data_generator.py` to emit a ~50 MB intermediate dataset first
- generation plus training measured at about five minutes locally
- it produces a **different** model from the one the application was tested
  against (8.5 MB vs the committed 17.9 MB, different validation scores)

So `models/adr_model.pkl` is committed and copied into the image. The build
fails loudly if that file is missing or too small, rather than deploying a
service whose `/health` would report the model as unloaded.

### Dependency pins are pickle-critical

`requirements.txt` previously pinned numpy 1.26 and scikit-learn 1.5, while the
committed model had been trained under numpy 2.3 / scikit-learn 1.7. A numpy 2.x
pickle cannot be read by numpy 1.x, so the container started, passed its
liveness probe, and served every page - but `/health` reported
`ml_model.loaded = false` and `/predict` was dead:

```
InconsistentVersionWarning: unpickle estimator from version 1.7.2 when using version 1.5.0
ERROR: <class 'numpy.random._pcg64.PCG64'> is not a known BitGenerator module
```

The pins now match the training environment, and the base image is
`python:3.13-slim` for the same reason. **If you retrain the model, regenerate
the pins from the environment you trained in.**

The build guards against this: it imports `MLService` and fails the build unless
the model actually loads. A file-size check is not enough, because a wrong-version
pickle is the right size.

### Git LFS

The model artifacts used to be tracked by Git LFS. They no longer are, because
Render does not reliably fetch LFS objects during a clone: the build context
would contain a 133-byte pointer instead of the model. `*.pkl` was removed from
`.gitattributes` and the real file committed. **Do not re-add `*.pkl` to LFS.**

## Environment variables

Set in the dashboard:

| Key | Notes |
|---|---|
| `NVIDIA_API_KEY` | Required for AI narratives. Without it the app still runs and every AI feature serves deterministic rule-based output. |

Declared in `render.yaml`, override only if you need to:

| Key | Default | Purpose |
|---|---|---|
| `NVIDIA_BASE_URL` | `https://integrate.api.nvidia.com/v1` | NIM OpenAI-compatible endpoint |
| `NVIDIA_MODEL_NAME` | `nvidia/nemotron-3-super-120b-a12b` | Primary model |
| `NVIDIA_FALLBACK_MODEL` | `nvidia/nemotron-3-ultra-550b-a55b` | Tried when the primary errors. Empty disables it. |
| `NVIDIA_TIMEOUT` | `30` | Per-attempt budget for every model except the last |
| `NVIDIA_LONG_TIMEOUT` | `120` | Budget for the final attempt, which generates a full narrative |
| `NVIDIA_ENABLE_THINKING` | `false` | Reasoning stream; unwanted in clinical output and costs latency |
| `SECRET_KEY` | generated | Flask secret |
| `LOG_LEVEL` | `INFO` | |

### A note on model choice

The 120B leads deliberately. `nemotron-3-ultra-550b-a55b` is persistently
capacity-limited: measured repeatedly against a valid key, it returned "Service
temporarily overloaded" or timed out on **every** attempt without once producing
a narrative, while costing `NVIDIA_TIMEOUT` seconds before failing over. The
120B answers in roughly 7-11 seconds.

The 550B remains the fallback rather than being dropped, for when it does have
capacity. To try it as the primary again:

```
NVIDIA_MODEL_NAME=nvidia/nemotron-3-ultra-550b-a55b
NVIDIA_FALLBACK_MODEL=nvidia/nemotron-3-super-120b-a12b
```

Both endpoints can return 503 at the same time, in which case the deterministic
rule-based output is served and `ai_generated` is `false`. That is NVIDIA-side
capacity, not a key problem.

## Resource sizing

The `free` plan has 512 MB of RAM. Measured on the built image, the service
idles at about **257 MB** with the model loaded, so it fits with headroom. The
image itself is around 830 MB.

Gunicorn runs one worker with four threads (`gthread`). Threads rather than
workers because the report page fires three concurrent LLM calls that each block
for tens of seconds, and extra workers would each load their own copy of the
model.

Free instances also spin down when idle; the first request afterwards pays a
cold start that includes loading the model.

## Verifying a deploy

```bash
BASE=https://<your-service>.onrender.com

curl -s $BASE/health | jq          # ml_model.loaded must be true
curl -s -o /dev/null -w '%{http_code}\n' $BASE/            # 200, SPA shell
curl -s -o /dev/null -w '%{http_code}\n' $BASE/assessment  # 200, deep link
curl -s $BASE/sample_data/high_risk | jq .name             # "Harold Wilson"
```

`/live` and `/ready` are also available for probes; the container's own
`HEALTHCHECK` uses `/live`.

### Diagnosing "the API key is not working"

`/health` reports the AI service under `components.ai_service`. Make one AI call
first (loading the report, or `POST /api/chat`), then read it - the fields only
populate once a call has been attempted:

| `status` | Meaning | Fix |
|---|---|---|
| `offline_fallback_active` | No key reached the process. `configured: false`. | Set `NVIDIA_API_KEY` in the Render dashboard, then redeploy. A blueprint variable marked `sync: false` is prompted for, not set automatically. |
| `configured_untested` | Key present, no call made yet. | Trigger an AI action and re-check. |
| `error` | Key present but calls fail. `last_error` gives the reason. | **401 with a key you know is good: the process is stale.** The key is read once when `AIService` is constructed, so editing `.env` or the dashboard does nothing until Flask restarts. Restart, then retry. A 403 means the key is genuinely rejected; regenerate it. A 429 means credits or rate limit. A 503 is NVIDIA capacity - retry. |
| `connected` | Working. `last_success_at` shows when. | - |

The key never appears in this output, and it is never logged.

Note that `.env` is deliberately excluded from the image, so a key that works
locally proves nothing about the deploy: on Render the value must come from the
dashboard.

## Running the image locally

```bash
docker build -t phenorx .
docker run --rm -p 5000:5000 -e NVIDIA_API_KEY=your-key phenorx
```

Then open <http://localhost:5000>. To rehearse exactly what Render does, inject
the port the way it will:

```bash
docker run --rm -p 5000:8080 -e PORT=8080 -e NVIDIA_API_KEY=your-key phenorx
```

The image was verified this way: `/health` returns 200 with
`ml_model.loaded = true`, all 17 routes serve, an unknown `/api/*` path still
returns a JSON 404, and `/predict` returns the same result as a local run.

## Known limitations

- **No database.** Saved assessments live in an in-memory store, so they are
  lost on restart and are not shared between instances. Anything needing real
  persistence requires adding a database first.
- **No authentication.** Every endpoint is public. Add auth before putting real
  patient data anywhere near this.
- **The model is trained on synthetic data** and has not been externally
  validated.
